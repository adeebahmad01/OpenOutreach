# CLAUDE.md

## Rules

- **Python env**: Always use `.venv/bin/python` (not system `python3`).
- **Commits**: No `Co-Authored-By` lines. Single-line messages (no body).
- **Dependencies**: Managed in `requirements/*.txt` (used by local dev and Docker).
- **Docs sync**: When modifying code, update CLAUDE.md and ARCHITECTURE.md to reflect changes.
- **No memory**: Never use the auto-memory system (no MEMORY.md, no memory files). All persistent context belongs in CLAUDE.md or ARCHITECTURE.md.
- **Error handling**: App should crash on unexpected errors. `try/except` only for expected, recoverable errors. Custom exceptions in `exceptions.py`.
- **No API backward compat**: Project has no external users yet — don't preserve old Python APIs, function signatures, or import paths. Rename, delete, and rewrite freely; no shims or re-export modules. DB schema changes still go through Django migrations as normal — existing installs must upgrade cleanly.
- **Migrations at the end**: During a multi-file change, let the models settle first — generate migrations in one pass at the end of the sweep, then run the suite. Don't hand-write a migration mid-change.

## Project Overview

OpenOutreach — a self-hosted, **email-first** AI sales agent that learns your ICP and runs the whole funnel with **zero platform-ToS surface** (browserless; no social-network account, no scraping):

**define ICP → discover → qualify → rank → find email → agentic email from your own mailbox.**

- **Discovery** is a licensed source — BetterContact **Lead Finder** (ICP search returns firmographic profiles, no emails, billed nothing).
- **Qualification** is the crown jewel — per-campaign **GPR + BALD active learning** over 384-dim embeddings, decided by an LLM.
- **Enrichment** is the one paid step — BetterContact resolves a work email for the top-ranked leads only (one credit per verified hit), fronted by a free cross-operator cache (the hub).
- **Outreach** is agentic email from mailboxes the user owns (SMTP send + IMAP reply-reading), driven by **one** LLM outreach agent that owns the whole thread — cold open and every reply — and whose job is **Mom Test research, not selling**: learn how the lead works today, never pitch unprompted. Every send carries the sending box's `Mailbox.signature`, then the **opt-out line** (a plain-text "reply unsubscribe" line — the body-side half of `List-Unsubscribe`), then the always-on `ATTRIBUTION` line (`Sent with OpenOutreach` — no URL, two blank lines below the signature) — all appended in `emails/sender.py`, in the order body → signature → opt-out → attribution; the agent itself never signs. The send log records metadata (from/to/subject/Message-ID) for every send, **plus what the agent generated on the operator's own campaigns** — the composed subject and body only, not the assembled message: signature, opt-out and attribution are identical on every send, so logging them repeats what the operator already knows and buries the one part that differs per lead. **Freemium sends stay metadata-only**, on the same reasoning that denies them a BCC: that outreach is OpenOutreach's own conversation with someone who is not the operator's contact. The campaign is passed to `send_email` explicitly rather than inferred from `bcc` — `operator_bcc` returns `None` both for freemium *and* for an operator who never set an address, so keying off it would silently drop the log for the second — and the parameter defaults to `None`/metadata-only, so a new call site cannot leak a body by forgetting to think about it.

Django + Django Admin own the CRM/ORM (models are this project's); pydantic-ai drives the agents.

## Architecture (quick reference)

For detailed module docs, see `ARCHITECTURE.md`.

- **Entry**: `manage.py` — stock Django management; bare `python manage.py` (no subcommand) defaults to `rundaemon`. The `rundaemon` command (`core/management/commands/rundaemon.py`) runs: migrate (+ `setup_crm`) → onboard if incomplete → validate → `run_daemon`. **Onboarding** (`core/onboarding.py`) is interactive and email-first — product/objective → LLM (live-verified) → **mailbox** (paste app passwords → SMTP auth-check) → **signature** (per-box sign-off, asked once per never-asked box; keyed on NULL so a declined `""` sticks) → **BetterContact key** → **your email** → country → newsletter/legal. Both the mailbox and the BetterContact key are **mandatory** (BetterContact powers *both* discovery and enrichment). The `account` step asks the operator's **own email** (required) — the human's inbox, stored as `User.email` and used as the newsletter target + contacts key + BCC-copy target on the operator's **own** campaigns (never on freemium — `emails.sender.operator_bcc`); it is deliberately **distinct** from the mailbox `from_address` (the sending identity). The operator `User` is created only after a mailbox exists. Built as an ordered list of idempotent `Step`s (`is_done`/`run`, persist-as-you-go) that resume where they left off; interactive prompt primitives vendored in `onboarding_wizard.py` (no external `openoutreach` dep).
- **State machine**: `crm/models/deal.py:DealState` (OpenOutreach-owned `TextChoices`) — `QUALIFIED → READY_TO_FIND_EMAIL → FINDING_EMAIL → READY_TO_EMAIL → EMAILED → COMPLETED / FAILED / UNSUBSCRIBED`. The GP confidence gate promotes `QUALIFIED → READY_TO_FIND_EMAIL` (rationing the paid lookup). The paid lookup is a **two-step async handshake**: `buy_address` resolves free-hub-first (hit → `READY_TO_EMAIL` directly) else fires a provider job and parks the deal at `FINDING_EMAIL`; `check_lookup` then polls the job's `request_id` — hit → `READY_TO_EMAIL`, miss → `NO_EMAIL_BETTERCONTACT` (its own terminal, **no reason and blank outcome** — the lead was an LLM fit positive and only *reachability* failed, so the ML labeler keeps it at label=1), couldn't-run → back to `READY_TO_FIND_EMAIL`. **A still-running job is never abandoned**: there is no deadline and no attempt limit, the step just doubles `not_before` on the same `request_id` while the deal waits at `FINDING_EMAIL`. The deadline used to revert the deal instead, which put it back in the pool for a *second* paid job — a hot resubmit loop that turned a provider outage into 418 submits and 4,512 polls in a week for ~40 leads, none terminating. Doubling makes waiting cheap (a week = 17 polls) and refuses to mislabel a provider outage as an unreachable lead. `COLLECT_BACKOFF_MAX_S` (a month) rails the *interval* only, so `datetime` can still represent the schedule. The job handle + poll backoff live **on the deal** (`lookup_request_id`, `lookup_attempt`, `not_before`), so the wait gates that one row. The first email sends and parks at `EMAILED`, and **nobody is ever chased**: the deal becomes actionable again only if the recipient replies, where the same agent picks send/complete/suppress. The agent still sees the thread's age in working days (`business_days_between`). `Outcome` (converted/not_interested/wrong_fit/…) on `Deal.outcome`; `Lead.disqualified=True` = permanent account-level exclusion; LLM rejections = `FAILED` + `wrong_fit` (campaign-scoped). `UNSUBSCRIBED` is the sibling of `NO_EMAIL_BETTERCONTACT` on the far side of the send — a fit positive whose reachability the *recipient* ended — so it too leaves `outcome` blank and keeps label=1; the enforcement lives on `Lead.disqualified` (cross-campaign) rather than on the state, which would bind one campaign only. *(The retired connect leg — browser, the network's private API, connect/check_pending, the browser CLI — was removed; the `legacy` app is a model-less migration-history anchor.)*
- **Send pacing + capacity**: three guards, because receivers punish *rate* and *volume* separately and a recipient reads the *hour*. **Hours** — `core/sending_window.py:within_sending_window`, asked pool-wide at the top of `Mailbox.objects.free_for_first_email`: a **first email** leaves only Mon–Fri, 08:00–20:00, in the **operator's** local time (`SiteConfig.country_code` → `pytz.country_timezones`, first zone for multi-zone countries; UTC if unset). Replies, discovery, lookups and the mail pass are exempt and run 24/7, so the queue is stocked overnight and answers are never held until Monday. A 03:00 opener is a machine announcing itself, and the reinstated window is the Playwright-era active hours minus their mistake — they gated the whole loop, this gates one step. The idle line names the gate when it is shut. **Rate** — `Mailbox.next_send_at`, rewritten by `emails/steps/send.py` after each first email as 3 min + `U[30s, 90s]` → 3.5–4.5 min, ~15/hour (tightened from the old 3–8 min band to pay for the 12-hour window). **Per box** rather than pool-wide (the daily ceiling is per box too, and two mailboxes are two sending identities), and **first emails only** — replies ignore it. Without it the daemon drains a day's queue at its own loop time (measured on a live box: ~11s apart, 40 messages inside one hour, several times what Gmail tolerates). **Volume** — `Mailbox.sent_today()` counts **people first contacted today** (each thread's first outgoing message, kept if it falls today, over distinct leads — so replies are free and one person reached twice counts once), against a per-box ceiling that is **measured, not configured**: `emails/warmth.py` reads the box's own Sent folder (p75 of days it actually sent, ×1.5 when the receiver hasn't pushed back, floored at 5 and railed at `WARM_CEILING_SENDS`, which is **computed** from the pacing and the window rather than declared — `SEND_WINDOW_SECONDS / MEAN_SEND_INTERVAL_SECONDS` = 43200/240 = **180** today, so widening either widens the rail and no second constant restates the arithmetic. It was a declared 50, the top of a 30–50/day band this repo never measured, which pinned volume an order below the rate and made the two guards redundant) into `Mailbox.daily_limit` (same column, now measured rather than configured), refreshed daily by `cycle.refresh_capacities_if_due`. Reading the Sent folder rather than our own ledger is the point — the receiver counts every message the box emits. Feedback comes from `emails/delivery_policy.py` and lands in the **mail log**: every send is written to `Message` before it is attempted and the receiver's answer is recorded against it as a `DeliveryEvent` — the `250` with its queue id, or a refusal classified from the SMTP **enhanced status**. A 4xx deferral is routine and costs nothing, `550 5.4.5`/`5.7.x` pause the box for the day, and transport/auth failures are explicitly *not* reputation signals so a flaky network can't throttle a healthy box. A **bounce** is now a verdict too (it arrives hours later as ordinary mail, which is why the exception-path-only `SendVerdict` saw 0 rows against 590 sends), and a box bouncing above `WARM_BOUNCE_TOLERANCE` has its capacity **halved** rather than merely held.
- **Opt-out + suppression**: every outbound message advertises a working way to leave, and every opt-out is honoured permanently. **Advertised** two ways on the same message, because each reaches recipients the other misses: a `List-Unsubscribe: <mailto:{local}+unsub@{domain}?subject=unsubscribe>` header, which is what receiving filters read and what Gmail renders its own button from, and a visible reply-line in the body for the clients that render no button. Both work by the same mechanism — put an exit in front of someone who wants one, so they take it instead of the spam button, complaint rate being the dominant reputation input. **No postal address**: it is a CAN-SPAM requirement with no measurable filter effect, and this is a deliverability feature (see the history card `2026-08-03-p1-e2-list-unsubscribe-and-opt-out`). The URI is a **`mailto:`, never an `https:`** — RFC 8058 one-click needs an HTTPS endpoint accepting POST, the self-hosted daemon has no web surface, and routing unsubscribes through the hub would make every install call home; `List-Unsubscribe-Post` is therefore deliberately absent (it is only valid alongside `https:`, and one-click binds bulk senders at 5,000+/day). **The alias assumes Gmail-style plus-addressing** — `s@d` advertises `s+unsub@d`, which delivers to the same INBOX the daemon already reads. Gmail/Workspace route `+` tags and are both the default hosts and what IceMail provisions, so it holds for the boxes this runs on; a provider that *rejects* them would bounce the opt-out and earn a spam complaint from someone who thinks they unsubscribed. Nothing verifies the round-trip at onboarding — **a non-Gmail box is the case to check by hand**. **Detected** two ways, because there are two kinds of event: a *client-generated* unsubscribe carries no threading headers, so a threaded reader could never see it — the **mail pass** (`emails/mail_pass.py`) mirrors it like any other message and `classify.py` recognises the `+unsub` alias, with `project.py` honouring it; the pass resumes from `FolderCoverage` (per `(mailbox, folder)`) and runs every `MAIL_PASS_INTERVAL_S` off the cycle; a *worded* unsubscribe threads normally and reaches the outreach agent, which has a `suppress` action alongside send/mark_completed. The two cover each other — the first is robust because the mail comes from the address we mailed, the second because it matches on thread, not address. **Enforced** on `Lead.disqualified` (permanent, account-level, cross-campaign), which eleven candidate queries already filter, so reuse inherits eleven correct guards instead of adding eleven that could be missed; `core.db.leads.suppress_email` suppresses **every** lead holding the address (`Lead.email` has no unique constraint, matched case-insensitively) and moves their open deals to `UNSUBSCRIBED`, leaving already-closed deals alone. Belt-and-braces `sender.suppressed(lead)` re-reads the row immediately before both sends — the upstream filters are convention, not DB-enforced (`pipeline/qualify.py:18`), and the agent runs for seconds. A **hard bounce must not** set `disqualified`: that binds to the address, not the person, and would block a replacement address found later.
- **The mail log** (`emails/models/maillog.py` + `sync.py`/`classify.py`/`project.py`): **the record and the interpretation are separate objects.** Every message a mailbox emits or receives is a `Message` row keyed on `(mailbox, message_id)` — never the UID, which is provenance only — written *before* anything decides what it is; `kind` + `classifier_version` are the reading, and `processed_at IS NULL` is **pending**, the third state whose absence let nine days of lost mail look like nine quiet days. The pass is three jobs in order: **sync** (IMAP → rows, the only network step; a message that cannot be fetched stops the walk instead of being stepped over, and the cursor advances only over what was stored), **classify** (pure and versioned over stored bytes — bump `CLASSIFIER_VERSION` and history is *repaired*, not just future mail), **project** (bounces → `DeliveryEvent`, opt-outs → suppression). Threading is union-find over Message-IDs (`threads.py`), so a reply carrying only `In-Reply-To` — which names the *newest* message, not the root — still reaches its deal; `Deal.thread` replaces `email_message_id` and `ChatMessage` is absorbed into `Message` (a turn *is* a message in an email-only product, and two tables meant dual writes that could disagree). `Thread.turns()` filters to `human_reply`/`outbound`, so an NDR can never reach `chat_summary`, the agent's context or `unanswered_replies`. **Only our conversation is stored**: mail naming an id we minted, the `+unsub` alias, mail from an address this box has written to, or a non-delivery report — and a folder's first walk starts at `UIDNEXT - 1`, so connecting a real mailbox does not mirror its history. `manage.py mailreport` answers "how many messages have I processed against how many exist?" and "what is my bounce rate?".
- **The cycle**: `core/cycle.py`. **A queue is a status, not a table** — work is found by asking the deals what they need, so nothing is minted and no row's timestamp can gate another. The loop is `read_mail_if_due` → `refresh_capacities_if_due` → `run_one_action(next campaign)` → `sleep(CYCLE_SECONDS)`, one action per cycle. `run_one_action` walks one ordered hierarchy and stops at the first thing it can do, so priority *is* that order: **1** `FINDING_EMAIL` → `check_lookup` (`not_before` elapsed), or `reclaim_lookup` → `READY_TO_FIND_EMAIL` when the deal carries no `lookup_request_id` — there is no job to poll and no credit was spent, and the row used to *skip* those, stranding them in a state nothing else claims while they still counted against the day's send headroom (two deals, 206h) · **2** `EMAILED` with an unanswered reply → `answer_reply` · **3** `READY_TO_EMAIL` → `send_first_email` (a box is free) · **4** `QUALIFIED` → `promote_to_ready` · **5** `READY_TO_FIND_EMAIL` → `buy_address` (room today) · **6** the campaign itself → `top_up` (room today). Unlisted states are terminal and cost nothing, including `EMAILED` with no reply. Steps live in `emails/steps/` (`lookup.py`, `send.py`, `reply.py`) and `core/pipeline/top_up.py`; each takes one entity and returns the next `DealState` or `None`, and `cycle._apply` does one `deal.save()` so a transition and its audit fields commit together. Steps are **total** — the loop's `try/except` is a bug backstop, not a retry policy; a step that wants to wait writes `deal.not_before`, which is the only retry mechanism there is. `HALTING_ERRORS` (`ModelHTTPError`) stops the daemon loudly instead, or a bad LLM key would retry every 5s forever behind an `alive` line. **Rows 5 and 6 share the only spend gate** (`room_to_send_today`): never buy an address, and never spend an LLM call qualifying, for someone there is no room to email today — "heading for a send" being `READY_TO_EMAIL` plus in-flight lookups whose next poll lands within `COLLECT_TODAY_HORIZON_S`, so a stalled job can't wedge the pipeline shut for weeks. Campaigns take turns (`_rotate`); there is no share and no allocation, because with nothing minted in advance there is no budget to split. **The hierarchy is data** (`ROWS`, name + function), so each action logs the row that fired and its duration, every row logs its decision time at `debug`, and a cycle where nothing fires logs the pipeline counts against today's headroom once every `IDLE_LOG_INTERVAL_S` — the steps log what they *did*, so without this a row that takes twenty seconds to decline is invisible, and *no work* looks exactly like *work behind a gate*. Row 4 runs for **every** campaign, so `promote_to_ready` calls `predict_probs` on freemium's `KitQualifier` too — that method is on the `Qualifier` protocol (with `rank_profiles`/`explain`) precisely because leaving it on `BayesianQualifier` alone let a freemium campaign reach the gate and `AttributeError` every other cycle. *(Replaces the `Task` model, `core/scheduler.py`, `core/quota.py` and `core/session.py` — a token queue inherited from the Playwright era. On 2026-08-05 it slept 34 hours: two never-terminating polls had backed off 45h, were the only rows, and 55 ready deals with 70 sends of headroom had no token and so were not work.)*
- **No chasing**: a follow-up is *checking whether a reply came*; if none came, nothing is sent. The trigger is an inbound **turn** in the deal's thread newer than our newest outgoing one, written by the mail pass — no timer, no flag. This deletes `next_follow_up_at`, `add_business_hours`, the agent's `follow_up_hours` and `wait` action, and the whole opener-floor apparatus (`OPENER_FLOOR_FRACTION`, `_opener_reserve`): that floor existed only because follow-ups outranked openers on claim *and* were reserved off the top without bound, so once open threads accumulate faster than they close the owed count consumes every send — measured on a live install, 102 follow-ups and 1 first email in a week. Replies are also **exempt from the daily cap and from send spacing**: a reply is not cold volume, and answering within minutes of being written to is more human, not less. Unanswered threads rest at `EMAILED` forever at no cost, since nothing iterates them; a tighter policy later needs no bookkeeping now (`EMAILED`, no inbound, `email_sent_at` older than N).
- **ML pipeline**: GPR (sklearn) + BALD active learning + LLM qualification, over 384-dim FastEmbed vectors cached on `Lead.embedding`. Per-campaign GP models in `Campaign.model_blob`.
- **Discovery + enrichment**: `openoutreach/discovery.py` (Lead Finder `search`, free) uses the blocking `submit_and_poll` transport; `emails/bettercontact.py` (paid finder) splits it into `submit(query) → request_id` + `poll_once(request_id) → PollOutcome` so the daemon never blocks on a poll (`check_lookup` owns the backoff). **Discovery is one counted, add-only walk over keyword sets** — from first principles: Lead Finder is a *keyword index*, not a facet store (words inside one string AND, strings inside one list OR, field vs field AND), so the atom is a **single word**. A **node** is a set of `(field, token)` `Keyword` rows; its children are itself plus one more token; there is no remove move, because the frontier is global — every unfired child of every fired node in one pool — so a shallow node's untried siblings stay reachable without one. `discovery.filters_for(keywords, headcount)` is the only place a node becomes provider JSON: same-field tokens are **space-joined** (the narrowing move, and the generator of the best queries measured — `"founder cto"` counts 9,027 at near-perfect precision), different fields are separate keys, and the include-list OR is deliberately **unused** (a union reaches one ~10k window where the same values as separate queries reach one each). Axes are `lead_job_title` / `lead_seniority` / `lead_location`; `lead_industry` is **inert** (a nonsense value returns the identical count), `lead_function` is `lead_department` under a second name whose values are ORed (naming both *widens*), and `lead_department` has no source field on a lead row so no vocabulary could ever grow for it. The headcount band (`Campaign.headcount_min/max`) rides every node unchanged and is never searched. **A node's value is arithmetic over labels, and no model is involved**: `P̂(node) = (a + 2·P̂(parent)) / (a + b + 2)`, where `a`/`b` are the qualified/rejected leads whose `profile_text` contains all of the node's tokens — Laplace smoothing pointed at the **parent's rate** rather than at 0.5, so the parent supplies the level and the child's own counts move it off. **The `LabelStore` counts the campaign's anchors as positives**, and that is what makes the cold phase work at all: expansion only offers a token that has shared a *qualified* profile with the node, so a campaign that has never accepted anybody had no qualified profile, could not grow past its one-token seed nodes, fired queries too broad to qualify anyone, and therefore still had no qualified profile — a closed loop in which the seed's own tokens could never be conjoined into the precise query the walk exists to find. The synthetic ideal profiles are written in `profile_text`'s shape, so they tokenize like any lead and say which words describe the people this campaign wants — the same bargain the GP already takes, on the same evidence, with the same expiry (`BayesianQualifier` retires one stored profile per real acceptance and the field empties once real positives reach `ANCHOR_COUNT`, so the invented evidence thins out of the count at exactly the rate ground truth replaces it and no phase check is needed). They deliberately do **not** feed the vocabulary: an anchor is one flat string with no per-field structure, and splitting it by guess would file `united states` as a job title. Anchors say which words go *together*; only a real lead row says which field a word is searchable in. Selection draws `θ ~ Beta(a + 2·P̂(parent), b + 2·(1 − P̂(parent)))` per frontier node and fires the argmax (Thompson, but the Beta params *are* the estimate — one line, nothing to tune; `select.THOMPSON = False` gives greedy). **The GP no longer selects queries**: measured on ~4,100 parent→child edges with the GP fit on half the labels and every truth on the other half, counting wins outright (pearson 0.661 vs 0.450) and the GP adds nothing on top (0.660); residual anchoring is worth 0.02 at λ≈0.15 and is *worse than nothing* at λ=1. The GP stays the qualifier — it produces the `a`/`b` the walk counts. `core/pipeline/`: `icp.py` (the two cold-start priors from the same inputs — `generate_seed`: one LLM pass → the opening **keywords** + size band, the *only* LLM call discovery makes about queries, with the spec's phrases **split into single-word tokens** so `"Head of Growth"` becomes three separate one-token nodes rather than one near-empty three-token AND; `generate_anchors`/`ensure_anchors`: the ICP as synthetic ideal *profiles*, embedded as the GP's positives so a campaign whose every verdict is a rejection can fit at all — profiles not product prose because the space is one of lead embeddings, retired one per real acceptance), `vocabulary.py` (**growth is counting, not generation**: the vocabulary is the words appearing in profiles the LLM already accepted, one word per keyword, admitted at **df ≥ 2** — a floor that drops 65% of the vocabulary and loses *zero* good tokens, while removing a singleton tail that is mostly company names and would otherwise be 56% of the top of any embedding ranking. Runs every pass; no cadence knob, no high-water mark. A token's field is read from the row fields that *are* that axis (`discovery.KEYWORD_SOURCE_FIELDS` → `Lead.source_fields`), keeping the per-field vocabularies nearly disjoint; `lead_seniority` is seeded whole from the provider's closed 12-value list and never grown), `select.py` (**the selector, and it is arithmetic**: `LabelStore` (token sets + verdicts, loaded once per pass — hundreds of rows, so counting a node is a microsecond set-containment scan), `estimate`, `frontier`/`next_node` (one pool: deepening a vein and opening a fresh node are two rows scored the same way, not two policies needing an alternation rule), `expand` (children are the node plus one token that has shared a **qualified** profile with it — which bounds the frontier without a top-K cap and keeps every child a proposition the evidence can speak to), `seed_frontier` (no root: one depth-1 node per keyword, and the empty query is never fired since it matches everyone and its 10k window is the provider's famous-company head), `advance`/`retire`/`token_key`), `discover.py` (`discover(campaign, qualifier)`: ensure vocabulary + frontier → draw a node → page it → harvest and expand, or classify the empty page and retire, then try the next node; `qualifier` is accepted and ignored). **Retirement is a corpus fact, never a model fact** — nothing is retired for scoring badly, only for emptiness, and *which* emptiness depends on the offset because the provider answers `0` for all of them: **offset 0** (after one spaced retry) = the index matches nobody → `dead`, subtree pruned (a superset matches a subset of people); **below the 10k reach cap** = the vein drained → `drained`, subtree pruned too (every match is already a `Lead` here); **at the cap** = Elasticsearch's `max_result_window`, not the end of the population → `drained` but the **subtree stays**, since adding a token opens a fresh window. The fourth case is not an answer: rows empty while `summary.leads_found` is positive is a **transport artifact** (a burst answered a 71M-lead query with an empty page in 0.0s) and never retires anything — `search()` returns `Page(leads, leads_found)` and the count is trusted **only at offset 0**. Then `qualify.py` (`run_qualification` — the balance-driven pick, which on a cold campaign runs against the anchored GP rather than against no model at all) → `ready_pool.py` (GP gate; `min_gp_confidence` is the paid-lookup spend gate **and nothing else**) → `top_up.py` (**one** unit of work per call — the cycle is the loop that used to live here. `top_up` is the *labelling* steering, the qualifier's own **explore/exploit** split: **cold phase** (`is_cold` — any anchor still standing) does **both** moves every pass — one query in, one label out — because rankings still lean on the anchors' guess, so no observed signal says a label beats a page; discovery's return is ignored, so only an empty pool stalls; and one countdown, `anchor_budget = max(0, ANCHOR_COUNT − n_real_positives)`, governs the synthetic positives — `_retire_anchors` drops one (newest first) per real acceptance and nothing tops them up. *(Discovery itself no longer has a cold phase — every node is scored the same way from day one, with the label store's base rate standing in for the level a root would supply.)* **the cold phase always exploits** — while any positive is an anchor the one goal is *more real positives* (each retires an anchor; the last one ends the phase), and the highest-P lead is the one most like the ideal profile, where BALD spends each call on the lead the model is most *confused* about, i.e. the one least like the ICP; the balance could not have chosen it anyway, since while the anchors were held at the rejection count `n_neg > n_pos` was false by construction. **The handover is one-for-one, not a cliff**: dropping every anchor on the first acceptance took the positive class from dozens to one against hundreds of rejections in a single step — the flat posterior anchors exist to prevent, one lead into the real evidence — so the padding now thins as ground truth replaces it and the phase lasts until real positives reach `ANCHOR_COUNT`, keeping the campaign in lead-search mode long enough to build a real positive class. **The clock is acceptances, never rejections**: the previous `n_neg − n_real_pos` budget was 0 on a campaign whose first verdict was an acceptance (so the first good lead dropped all three anchors at once, leaving a positive class of one that `_balance` pinned the training set to), and its top-up ran only under `is_cold`, which read the anchor count — an empty set switched off the only path that could refill it. Past the phase: **explore** (`neg ≤ pos`) BALD-labels the pool with **no gate**, **exploit** (`neg > pos`) qualifies the strongest lead clearing `min_gp_confidence` or `discover`s if none clears it). **Keyword injection survives but is vestigial**: a discovered lead is still embedded as `profile_text + keyword_terms(its retrieving node)` while `profile_text` (the LLM qualifier's input) stays clean — its original job was letting the GP score a never-run query by its keywords, and what keeps it now is only that every cached `Lead.embedding` was built that way. See the roadmap card `p1-e3-leadfinder-index-semantics-and-query-model-rethink` (supersedes `p2-e3-discovery-unified-gp-query-selection` and `p2-e3-discovery-empty-set-backoff`).
- **Contacts store (hub)**: `contacts/service.py` — an optional free `profile_url → email` cache at `hub.openoutreach.app`, tried *before* the paid finder and given back to on a fresh paid hit. Both calls are best-effort (outage/no-token → no-op) and gated on `has_mailbox()`. The give-back is **non-EEA only** and derived from the operator's onboarding country (`not is_eea_located`) — never a stored toggle; the server re-gates authoritatively. A per-operator token is earned on first contribution and stored in `SiteConfig.contacts_api_token` (never the repo).
- **Config**: `SiteConfig` DB singleton — `ai_model` (a pydantic-ai `provider:model` id, e.g. `anthropic:claude-sonnet-4-5-20250929`; bare `gpt-*`/`o1`/`o3`/`claude-*`/`gemini-*` auto-prefixed), `llm_api_key`, `llm_api_base` (only for `openai_compatible:*`), `bettercontact_api_key` (blank disables discovery + enrichment), `contacts_api_token`/`contacts_api_url`, `country_code` (the only persisted operator setting — drives timezone + email jurisdiction). `core/conf.py`: `CAMPAIGN_CONFIG` (ML defaults, incl. `min_gp_confidence` for the paid-step rank gate — which is **only** a spend gate; there is no discovery-interleave threshold and **no discovery cadence knob**, since growing the vocabulary is now a tokenize-and-count that runs every pass rather than an LLM call worth rationing), `COLLECT_BACKOFF_BASE_S`/`COLLECT_BACKOFF_MAX_S` (the lookup poll backoff — doubling, no deadline, MAX rails the interval only) and `COLLECT_TODAY_HORIZON_S` (past which a stalled lookup stops counting against today's send headroom) — paid spend is gated by send-headroom, not a cap, `MIN_SEND_INTERVAL_SECONDS`/`SEND_INTERVAL_JITTER_MIN_SECONDS`/`SEND_INTERVAL_JITTER_MAX_SECONDS` (the per-box 3.5–4.5 min gap between two *first* emails), `SEND_WINDOW_START_HOUR`/`SEND_WINDOW_END_HOUR` (8/20 — the operator-local hours a first email may leave, weekends shut), `WARM_*` (the measured per-box daily ceiling), `CYCLE_SECONDS`/`MAIL_PASS_INTERVAL_S` in `core/cycle.py`. `core/business_time.py` has **no knob** and now only *measures* (Mon–Fri, no public holidays): it tells the agent how old a thread is: with no chasing there is no gap left to schedule. The sending window borrows its Mon–Fri line — same calendar, different question.
- **Django apps** (all nested under `openoutreach/`, dotted `AppConfig.name`, short labels): `core` (engine — the cycle, operator lookup, Campaign/SiteConfig, llm, onboarding, ML, discovery/qualify pipeline, the outreach agent), `crm` (Lead + Deal), `chat` (model-less migration anchor — ChatMessage was absorbed into `emails.Message`), `emails` (discovery/enrichment client, Mailbox + import + SMTP/IMAP, **the mail log**, sender, the mail pass, the steps), `legacy` (model-less migration-history anchor). `contacts` is a service-only module (no models, not an installed app). One engine, one channel.
- **Data dir**: `data/` holds `db.sqlite3`. Docker mounts a volume at `/app/data`. Any command takes a global `--db PATH` (or `OPENOUTREACH_DB=…`) to run against a different SQLite file — `manage.py` strips the flag before Django's per-command parsing and `settings.py` reads the env var, creating the parent dir if needed.
- **Docker**: `python:3.12-slim` multi-stage build with `uv`; no browser, no VNC. `compose/openoutreach/Dockerfile`. `BUILD_ENV` arg selects requirements.
- **CI/CD**: `.github/workflows/tests.yml` (pytest), `deploy.yml` (**every push to `main`**, plus `v*` tags → `make docker-test` → build + push `ghcr.io/eracle/openoutreach` tagged `latest` + `sha-<pushed tip>` → `repository-dispatch: image-updated` to the hub repo). **There is no release gate: merging to `main` republishes `:latest`**, so code *and schema migrations* reach anyone pulling `latest` on merge, not on a tag. No `v*` tag has ever been cut, so no semver tag exists to pin or roll back to.
