# CLAUDE.md

## Rules

- **Python env**: Always use `.venv/bin/python` (not system `python3`).
- **Commits**: No `Co-Authored-By` lines. Single-line messages (no body).
- **Dependencies**: Declared in `pyproject.toml` (`[project.dependencies]`, dev extras under `[project.optional-dependencies]`). The `requirements/*.txt` files are gone.
- **The tool is CLI-first, installed from PyPI** — `uvx openoutreach` / `pip install openoutreach`, entry point `openoutreach/__main__.py:main`. **Docker is the server deploy only** (`docs/infrastructure.md` §7 in `openoutreach-docs`); development and tests run natively. See the card `p1-e2-cli-entry-points`.
- **Docs sync**: When modifying code, update CLAUDE.md and ARCHITECTURE.md to reflect changes.
- **No memory**: Never use the auto-memory system (no MEMORY.md, no memory files). All persistent context belongs in CLAUDE.md or ARCHITECTURE.md.
- **Error handling**: App should crash on unexpected errors. `try/except` only for expected, recoverable errors. Custom exceptions in `exceptions.py`.
- **No API backward compat**: Project has no external users yet — don't preserve old Python APIs, function signatures, or import paths. Rename, delete, and rewrite freely; no shims or re-export modules.
- **Migrations**: one `0001_initial` per app and no history before it — see *The cut* below. Existing installs upgrade cleanly **from that point on**; a DB created before it cannot upgrade past it, by decision. During a multi-file change, let the models settle first — generate migrations in one pass at the end of the sweep, then run the suite. Don't hand-write a migration mid-change.

## Project Overview

OpenOutreach — a self-hosted **lead finder that qualifies for you**, with **zero platform-ToS surface** (browserless; no social-network account, no scraping):

**define ICP → discover → qualify → rank → (optionally) resolve an address → export CSV.**

- **Discovery** is a licensed source — BetterContact **Lead Finder** (ICP search returns firmographic profiles, no emails, billed nothing). The walk over its keyword index is *counting*, not a model.
- **Qualification** is the crown jewel — per-campaign **GPR + BALD active learning** over 384-dim embeddings, decided by an LLM, which also **writes down why**. That reason is the product.
- **Enrichment** is the one paid step — BetterContact resolves a work email for the top-ranked leads only (one credit per verified hit), fronted by a free cross-operator cache (the hub). Optional: a lead with no address still exports.
- **The output is a file.** `manage.py export_leads --campaign NAME` → CSV in the column names Instantly and Smartlead already read. See *The lead export* below.

Django + Django Admin own the CRM/ORM (models are this project's); pydantic-ai drives the LLM calls.

### The cut (2026-08-19) — this project does not send email

The sending half was **ported to [OpenEmailSequence](https://github.com/eracle/OpenEmailSequence)**
(parked under `cold_outreach/` there, with a README mapping every dangling dependency). Gone from
here: the `emails` app entirely — `Mailbox`, SMTP/IMAP, the mail log (`Thread`/`Message`/
`DeliveryEvent`/`FolderCoverage`), the sender, the three send guards (hours/rate/volume), the
opt-out mechanisms — plus the outreach agent, `core/sending_window.py`, the `chat` and `legacy`
migration anchors, and the **freemium promo campaign** with its `KitQualifier` and HuggingFace kit.

Four consequences worth knowing before changing anything:

1. **Nothing gates a free step on a paid one.** Discovery and qualification are ungated; the old rule (*never qualify a lead there is no room to email today*) was the single line that made a mailbox-less install silently produce nothing. Don't reintroduce that shape.
2. **The opt-out duty left with the code.** A finder that contacts nobody is not the sender under CAN-SPAM/GDPR/CASL. `Lead.disqualified` survives as the export's exclusion filter, but nothing sets it automatically any more. The hub store's own suppression is separate and unaffected.
3. **The GP never trained on a market signal.** `get_labeled_arrays` reads the LLM's fit verdict alone, so losing replies and bounces cost the model nothing.
4. **The two prod daemons are pinned to the tag `pre-finder-cut`** and do not upgrade past it — the migration history was squashed, not migrated.

## Architecture (quick reference)

For detailed module docs, see `ARCHITECTURE.md`.

- **Entry**: `openoutreach/__main__.py:main` — the `openoutreach` console script, and the one entry point; it strips the global `--db` flag before Django's per-command parsing and defaults a bare invocation to `rundaemon`. `manage.py` is a thin shim over it for work inside a checkout. The `rundaemon` command (`core/management/commands/rundaemon.py`) runs: migrate (+ `setup_crm`) → onboard if incomplete → validate → `run_daemon`. **Onboarding** (`core/onboarding.py`) is interactive, **four steps**: product/objective → LLM (live-verified) → **BetterContact key** (mandatory — it powers *both* discovery and enrichment, so the barrier is an account, not a bill) → **your email** → country → newsletter/legal. The `account` step's address is the human's own inbox, stored as `User.email`, the newsletter target and the contacts-store key. Built as an ordered list of idempotent `Step`s (`is_done`/`run`, persist-as-you-go) that resume where they left off; prompt primitives vendored in `onboarding_wizard.py`. *(The `mailbox` and `signature` steps went with the sending leg — that was most of the install path, and behind the mailbox step stood the disclosure that the tool would send the maintainer's promo campaign from the operator's own mailbox.)*
- **State machine**: `crm/models/deal.py:DealState` — `QUALIFIED → READY_TO_FIND_EMAIL → FINDING_EMAIL → RESOLVED`, with `NO_EMAIL_BETTERCONTACT` and `FAILED` as the other terminals. **Every state below `RESOLVED` is terminal**, and `QUALIFIED` is already exportable: an address is an enrichment on top, never a precondition. The GP confidence gate promotes `QUALIFIED → READY_TO_FIND_EMAIL` (rationing the paid lookup — a **spend** gate and nothing else, never a quality score). The paid lookup is a **two-step async handshake**: `buy_address` resolves free-hub-first (hit → `RESOLVED` directly) else fires a provider job and parks the deal at `FINDING_EMAIL`; `check_lookup` then polls the job's `request_id` — hit → `RESOLVED`, miss → `NO_EMAIL_BETTERCONTACT` (its own terminal, **no reason and blank outcome** — the lead was an LLM fit positive and only *reachability* failed, so the ML labeler keeps it at label=1), couldn't-run → back to `READY_TO_FIND_EMAIL`. **A still-running job is never abandoned**: there is no deadline and no attempt limit, the step just doubles `not_before` on the same `request_id`. The deadline used to revert the deal instead, which put it back in the pool for a *second* paid job — a hot resubmit loop that turned a provider outage into 418 submits and 4,512 polls in a week for ~40 leads, none terminating. Doubling makes waiting cheap (a week = 17 polls) and refuses to mislabel a provider outage as an unreachable lead. `COLLECT_BACKOFF_MAX_S` (a month) rails the *interval* only, so `datetime` can still represent the schedule. The job handle + poll backoff live **on the deal** (`lookup_request_id`, `lookup_attempt`, `not_before`), so the wait gates that one row. `Outcome` is down to `wrong_fit`/`unknown`; `Lead.disqualified=True` = permanent account-level exclusion (a **different column** from `FAILED` — the export filters both); LLM rejections = `FAILED` + `wrong_fit` (campaign-scoped). *(Two legs have been removed: the connect leg with the browser channel, and the send leg — `READY_TO_EMAIL`/`EMAILED`/`COMPLETED`/`UNSUBSCRIBED` plus the reply outcomes — with `emails/*`. Dropping the reply outcomes also retired a live mislabelling: the reply step moved a deal to `COMPLETED`, not `FAILED`, so a "not interested" reply trained the GP as a **positive**.)*
- **The cycle**: `core/cycle.py`. **A queue is a status, not a table** — work is found by asking the deals what they need, so nothing is minted and no row's timestamp can gate another. The loop is `run_one_action(next campaign)` → `sleep(CYCLE_SECONDS)`, one action per cycle, with **no periodic side-effects** (the mail pass and the daily warmth re-measure both left with the sending leg). `run_one_action` walks one ordered hierarchy and stops at the first thing it can do, so priority *is* that order: **1** `FINDING_EMAIL` → `check_lookup` (`not_before` elapsed), or `reclaim_lookup` → `READY_TO_FIND_EMAIL` when the deal carries no `lookup_request_id` — there is no job to poll and no credit was spent, and the row used to *skip* those, stranding them in a state nothing else claims (two deals, 206h) · **2** `QUALIFIED` → `promote_to_ready` · **3** `READY_TO_FIND_EMAIL` → `buy_address` (a provider is configured) · **4** the campaign itself → `top_up`. Unlisted states are terminal and cost nothing. Steps live in `enrichment/lookup.py` and `core/pipeline/top_up.py`; each takes one entity and returns the next `DealState` or `None`, and `cycle._apply` does one `deal.save()` so a transition and its audit fields commit together. Steps are **total** — the loop's `try/except` is a bug backstop, not a retry policy; a step that wants to wait writes `deal.not_before`, which is the only retry mechanism there is. `HALTING_ERRORS` (`ModelHTTPError`) stops the daemon loudly instead, or a bad LLM key would retry every 5s forever behind an `alive` line. **Rows 2 and 4 have no gate at all, and that is the pivot**: they used to share `room_to_send_today` (*never buy an address, and never spend an LLM call qualifying, for someone there is no room to email today*), which was right while every lead ended in a send and was also the single line that made a mailbox-less install produce **nothing** — zero pool headroom, comparison never true, discovery and qualification silently stopped. Nothing replaced it: discovery is free, qualification costs the operator's own LLM key, and the loop is bounded at one unit of work per cycle. **Do not reintroduce a gate on a free step derived from a paid or absent one.** Campaigns take turns (`_rotate`). **The hierarchy is data** (`ROWS`, name + function), so each action logs the row that fired and its duration, every row logs its decision time at `debug`, and a cycle where nothing fires logs the pipeline counts once every `IDLE_LOG_INTERVAL_S` — *no work* otherwise looks exactly like *work behind a gate*. *(Replaces the `Task` model, `core/scheduler.py`, `core/quota.py` and `core/session.py` — a token queue inherited from the Playwright era. On 2026-08-05 it slept 34 hours: two never-terminating polls had backed off 45h, were the only rows, and 55 ready deals had no token and so were not work.)*
- **ML pipeline**: GPR (sklearn) + BALD active learning + LLM qualification, over 384-dim FastEmbed vectors cached on `Lead.embedding`. Per-campaign GP models in `Campaign.model_blob`. **It trains on the LLM's fit verdict and nothing else** (`get_labeled_arrays`: label 1 = any non-`FAILED` deal, 0 = `FAILED` + `wrong_fit`) — no market signal was ever in that loop, which is why handing sending away cost the model nothing. The correction loop is the human: read `reason`, edit the product description and the ICP.
- **Discovery + enrichment**: `openoutreach/discovery.py` (Lead Finder `search`, free) uses the blocking `submit_and_poll` transport; `enrichment/bettercontact.py` (paid finder) splits it into `submit(query) → request_id` + `poll_once(request_id) → PollOutcome` so the daemon never blocks on a poll (`check_lookup` owns the backoff). **Discovery is one counted, add-only walk over keyword sets** — from first principles: Lead Finder is a *keyword index*, not a facet store (words inside one string AND, strings inside one list OR, field vs field AND), so the atom is a **single word**. A **node** is a set of `(field, token)` `Keyword` rows; its children are itself plus one more token; there is no remove move, because the frontier is global — every unfired child of every fired node in one pool — so a shallow node's untried siblings stay reachable without one. `discovery.filters_for(keywords, headcount)` is the only place a node becomes provider JSON: same-field tokens are **space-joined** (the narrowing move, and the generator of the best queries measured — `"founder cto"` counts 9,027 at near-perfect precision), different fields are separate keys, and the include-list OR is deliberately **unused** (a union reaches one ~10k window where the same values as separate queries reach one each). Axes are `lead_job_title` / `lead_seniority` / `lead_location`; `lead_industry` is **inert** (a nonsense value returns the identical count), `lead_function` is `lead_department` under a second name whose values are ORed (naming both *widens*), and `lead_department` has no source field on a lead row so no vocabulary could ever grow for it. The headcount band (`Campaign.headcount_min/max`) rides every node unchanged and is never searched. **A node's value is arithmetic over labels, and no model is involved**: `P̂(node) = (a + 2·P̂(parent)) / (a + b + 2)`, where `a`/`b` are the qualified/rejected leads whose `profile_text` contains all of the node's tokens — Laplace smoothing pointed at the **parent's rate** rather than at 0.5, so the parent supplies the level and the child's own counts move it off. **The `LabelStore` counts the campaign's anchors as positives**, and that is what makes the cold phase work at all: expansion only offers a token that has shared a *qualified* profile with the node, so a campaign that has never accepted anybody had no qualified profile, could not grow past its one-token seed nodes, fired queries too broad to qualify anyone, and therefore still had no qualified profile — a closed loop in which the seed's own tokens could never be conjoined into the precise query the walk exists to find. The synthetic ideal profiles are written in `profile_text`'s shape, so they tokenize like any lead and say which words describe the people this campaign wants — the same bargain the GP already takes, on the same evidence, with the same expiry (`BayesianQualifier` retires one stored profile per real acceptance and the field empties once real positives reach `ANCHOR_COUNT`, so the invented evidence thins out of the count at exactly the rate ground truth replaces it and no phase check is needed). They deliberately do **not** feed the vocabulary: an anchor is one flat string with no per-field structure, and splitting it by guess would file `united states` as a job title. Anchors say which words go *together*; only a real lead row says which field a word is searchable in. Selection draws `θ ~ Beta(a + 2·P̂(parent), b + 2·(1 − P̂(parent)))` per frontier node and fires the argmax (Thompson, but the Beta params *are* the estimate — one line, nothing to tune; `select.THOMPSON = False` gives greedy). **The GP no longer selects queries**: measured on ~4,100 parent→child edges with the GP fit on half the labels and every truth on the other half, counting wins outright (pearson 0.661 vs 0.450) and the GP adds nothing on top (0.660); residual anchoring is worth 0.02 at λ≈0.15 and is *worse than nothing* at λ=1. The GP stays the qualifier — it produces the `a`/`b` the walk counts. `core/pipeline/`: `icp.py` (the two cold-start priors from the same inputs — `generate_seed`: one LLM pass → the opening **keywords** + size band, the *only* LLM call discovery makes about queries, with the spec's phrases **split into single-word tokens** so `"Head of Growth"` becomes three separate one-token nodes rather than one near-empty three-token AND; `generate_anchors`/`ensure_anchors`: the ICP as synthetic ideal *profiles*, embedded as the GP's positives so a campaign whose every verdict is a rejection can fit at all — profiles not product prose because the space is one of lead embeddings, retired one per real acceptance), `vocabulary.py` (**growth is counting, not generation**: the vocabulary is the words appearing in profiles the LLM already accepted, one word per keyword, admitted at **df ≥ 2** — a floor that drops 65% of the vocabulary and loses *zero* good tokens, while removing a singleton tail that is mostly company names and would otherwise be 56% of the top of any embedding ranking. Runs every pass; no cadence knob, no high-water mark. A token's field is read from the row fields that *are* that axis (`discovery.KEYWORD_SOURCE_FIELDS` → `Lead.source_fields`), keeping the per-field vocabularies nearly disjoint; `lead_seniority` is seeded whole from the provider's closed 12-value list and never grown), `select.py` (**the selector, and it is arithmetic**: `LabelStore` (token sets + verdicts, loaded once per pass — hundreds of rows, so counting a node is a microsecond set-containment scan), `estimate`, `frontier`/`next_node` (one pool: deepening a vein and opening a fresh node are two rows scored the same way, not two policies needing an alternation rule), `expand` (children are the node plus one token that has shared a **qualified** profile with it — which bounds the frontier without a top-K cap and keeps every child a proposition the evidence can speak to), `seed_frontier` (no root: one depth-1 node per keyword, and the empty query is never fired since it matches everyone and its 10k window is the provider's famous-company head), `advance`/`retire`/`token_key`), `discover.py` (`discover(campaign, qualifier)`: ensure vocabulary + frontier → draw a node → page it → harvest and expand, or classify the empty page and retire, then try the next node; `qualifier` is accepted and ignored). **Retirement is a corpus fact, never a model fact** — nothing is retired for scoring badly, only for emptiness, and *which* emptiness depends on the offset because the provider answers `0` for all of them: **offset 0** (after one spaced retry) = the index matches nobody → `dead`, subtree pruned (a superset matches a subset of people); **below the 10k reach cap** = the vein drained → `drained`, subtree pruned too (every match is already a `Lead` here); **at the cap** = Elasticsearch's `max_result_window`, not the end of the population → `drained` but the **subtree stays**, since adding a token opens a fresh window. The fourth case is not an answer: rows empty while `summary.leads_found` is positive is a **transport artifact** (a burst answered a 71M-lead query with an empty page in 0.0s) and never retires anything — `search()` returns `Page(leads, leads_found)` and the count is trusted **only at offset 0**. Then `qualify.py` (`run_qualification` — the balance-driven pick, which on a cold campaign runs against the anchored GP rather than against no model at all) → `ready_pool.py` (GP gate; `min_gp_confidence` is the paid-lookup spend gate **and nothing else**) → `top_up.py` (**one** unit of work per call — the cycle is the loop that used to live here. `top_up` is the *labelling* steering, the qualifier's own **explore/exploit** split: **cold phase** (`is_cold` — any anchor still standing) does **both** moves every pass — one query in, one label out — because rankings still lean on the anchors' guess, so no observed signal says a label beats a page; discovery's return is ignored, so only an empty pool stalls; and one countdown, `anchor_budget = max(0, ANCHOR_COUNT − n_real_positives)`, governs the synthetic positives — `_retire_anchors` drops one (newest first) per real acceptance and nothing tops them up. *(Discovery itself no longer has a cold phase — every node is scored the same way from day one, with the label store's base rate standing in for the level a root would supply.)* **the cold phase always exploits** — while any positive is an anchor the one goal is *more real positives* (each retires an anchor; the last one ends the phase), and the highest-P lead is the one most like the ideal profile, where BALD spends each call on the lead the model is most *confused* about, i.e. the one least like the ICP; the balance could not have chosen it anyway, since while the anchors were held at the rejection count `n_neg > n_pos` was false by construction. **The handover is one-for-one, not a cliff**: dropping every anchor on the first acceptance took the positive class from dozens to one against hundreds of rejections in a single step — the flat posterior anchors exist to prevent, one lead into the real evidence — so the padding now thins as ground truth replaces it and the phase lasts until real positives reach `ANCHOR_COUNT`, keeping the campaign in lead-search mode long enough to build a real positive class. **The clock is acceptances, never rejections**: the previous `n_neg − n_real_pos` budget was 0 on a campaign whose first verdict was an acceptance (so the first good lead dropped all three anchors at once, leaving a positive class of one that `_balance` pinned the training set to), and its top-up ran only under `is_cold`, which read the anchor count — an empty set switched off the only path that could refill it. Past the phase: **explore** (`neg ≤ pos`) BALD-labels the pool with **no gate**, **exploit** (`neg > pos`) qualifies the strongest lead clearing `min_gp_confidence` or `discover`s if none clears it). **Keyword injection survives but is vestigial**: a discovered lead is still embedded as `profile_text + keyword_terms(its retrieving node)` while `profile_text` (the LLM qualifier's input) stays clean — its original job was letting the GP score a never-run query by its keywords, and what keeps it now is only that every cached `Lead.embedding` was built that way. See the roadmap card `p1-e3-leadfinder-index-semantics-and-query-model-rethink` (supersedes `p2-e3-discovery-unified-gp-query-selection` and `p2-e3-discovery-empty-set-backoff`).
- **The lead export**: `core/export.py` + `manage.py export_leads` — the finder's **public output**, and Tier 0 of the boundary described by the `openoutreach-docs` card `p1-e3-leadfinder-sequencer-boundary`. The governing rule is that **our own sender gets no privileged path**: a sequencer, a CRM and a spreadsheet all read the same rows. **The column names are the importers', not ours** — Instantly and Smartlead both *require* `email`/`first_name`/`last_name` and recognise `company`/`title`/`website`/`linkedin_url`, mapping anything else to a custom variable, so the record is exactly `email, first_name, last_name, company, title, website, linkedin_url, reason, lead_id` and a file imports without column mapping. The internal model keeps its own names (`profile_url` is provider-agnostic on purpose; a `domain` is not a `website`) and `lead_record()` is the one translation — one schema cannot match N importers, so the mapping is a function, never a migration. CSV is a flattening of the JSON record, never a second schema (both from `RECORD_FIELDS`; `None` → empty cell). **There is no score column and the export touches nothing but the DB** — exporting the GP posterior was a category error (`min_gp_confidence` is the paid-lookup *spend* gate and nothing else; the fit verdict is the LLM's, already present as `reason`), and it cost an O(n³) `qualifier_for` fit — minutes on the live 2,538-deal campaign — which also calls `ensure_anchors`, so a cold campaign would have spent LLM calls and mutated state from a read-only command. The **Deal** is the unit (the `reason` is per-campaign). **A Deal is not an endorsement**: `DealState.FAILED` (the LLM's campaign-scoped rejection) and `Lead.disqualified` (the permanent opt-out) are *different columns*, and the first shipped version filtered only the second — exporting 1,944 rows whose `reason` read "does not align well with the target market". Both are excluded, always, with no flag to include them. The command takes one argument (`--campaign`) and writes CSV to stdout. **The boundary is one-way** (2026-08-19): leads leave, nothing comes back. There is no inbound endpoint and no event vocabulary — reply outcomes are conversation states belonging to whoever sent the mail, and a finder that never contacts anyone is not the sender under CAN-SPAM/GDPR, so suppression stays with the sequencer (Instantly and Smartlead both block a suppressed address at import). The GP therefore keeps training on the LLM's fit verdict alone; `get_labeled_arrays` has never seen a market signal, so nothing was lost. `lead_id` keeps the door open if that is revisited — the one candidate is `bounced`, which grades the row we emitted rather than the message. Import dedupe is **opt-in** on Smartlead and undocumented on Instantly, so every adapter's docs must tell the operator to enable it.
- **Lead identity + Company**: `Lead.full_name`/`first_name`/`last_name`/`job_title` (all nullable — `NULL` means the provider never told us) and `Lead.company` → `crm.Company`, a shared employer row keyed on `Company.key` (the lowercased domain, or `name:<name>` when no domain was reported). They serve the export and the record the product keeps, and are deliberately **out of** `profile_text` and the embedding: a name carries no ICP signal and would only give the GP noise. **Nothing splits a name in-house** — discovery reports one `contact_full_name`, and the paid enrichment response reports the real `contact_first_name`/`contact_last_name` at no extra call or credit (`enrichment/lookup.py` writes them on a hit). A hub-cache resolution never reaches that provider, so its name parts stay `NULL`; they feed a sequencer's `{{first_name}}` merge tag, where a guess lands in someone's cold email. The **enrichment query stays URL-only** by decision — the provider accepts name/company and resolves better with them, but the less of a lead's record leaves for a third party the better, and URL-only measures ~42% usable. `Company` rows are *what the provider said*, not verified truth (Lead Finder fuzzy-matches them), and a firm seen once with and once without a domain produces two rows — a known cost of the simple key.
- **Contacts store (hub)**: `contacts/service.py` — an optional free `profile_url → email` cache at `hub.openoutreach.app`, tried *before* the paid finder and given back to on a fresh paid hit. Both calls are best-effort (outage/no-token → no-op). The give-back is **non-EEA only** and derived from the operator's onboarding country (`not is_eea_located`) — never a stored toggle; the server re-gates authoritatively. A per-operator token is earned on first contribution and stored in `SiteConfig.contacts_api_token` (never the repo).
- **Config**: `SiteConfig` DB singleton — `ai_model` (a pydantic-ai `provider:model` id, e.g. `anthropic:claude-sonnet-4-5-20250929`; bare `gpt-*`/`o1`/`o3`/`claude-*`/`gemini-*` auto-prefixed), `llm_api_key`, `llm_api_base` (only for `openai_compatible:*`), `bettercontact_api_key` (blank disables discovery + enrichment), `contacts_api_token`/`contacts_api_url`, `country_code` (the only persisted operator setting — drives the email jurisdiction rules). `core/conf.py`: `CAMPAIGN_CONFIG` (ML defaults, incl. `min_gp_confidence` for the paid-step rank gate — which is **only** a spend gate; there is no discovery-interleave threshold and **no discovery cadence knob**, since growing the vocabulary is now a tokenize-and-count that runs every pass rather than an LLM call worth rationing), `COLLECT_BACKOFF_BASE_S`/`COLLECT_BACKOFF_MAX_S` (the lookup poll backoff — doubling, no deadline, MAX rails the interval only), `CYCLE_SECONDS` in `core/cycle.py`. **There is no spend cap on the paid lookup**: it used to ride on send headroom, and with no sending leg nothing replaced it — what bounds the spend is the operator's prepaid provider balance, which we cannot see. *(Gone with the sending leg: `WARM_*`, `MIN_SEND_INTERVAL_SECONDS`/`SEND_INTERVAL_JITTER_*`, `SEND_WINDOW_*`, `COLLECT_TODAY_HORIZON_S`, `MAIL_PASS_INTERVAL_S`.)* `core/business_time.py` has **no knob** and only *measures* (Mon–Fri, no public holidays); with the agent gone the pipeline no longer calls it.
- **Django apps** (nested under `openoutreach/`, dotted `AppConfig.name`, short labels): **just two** — `core` (engine — the cycle, operator lookup, Campaign/SiteConfig, llm, onboarding, ML, discovery/qualify pipeline, the lead export) and `crm` (Lead + Company + Deal). `enrichment` and `contacts` are service-only modules (no models, not installed apps). *(`emails`, `chat` and `legacy` are gone — see* The cut *above.)*
- **Data dir**: holds `db.sqlite3`. **Installed, it is `~/.openoutreach/data`; in a checkout it is `data/`** — `settings.py` tells them apart by whether `manage.py` sits beside the package, because from a wheel `ROOT_DIR` is site-packages and no operator's CRM belongs there. The Docker image names the path outright (`OPENOUTREACH_DB=/app/data/db.sqlite3`) and mounts a volume at `/app/data`. Any command takes a global `--db PATH` (or `OPENOUTREACH_DB=…`) to run against a different SQLite file; `settings.py` creates the parent dir if needed. SQLite runs in **WAL** so a second process (`status`) can read while the daemon writes.
- **Docker**: `python:3.12-slim`, two stages — a venv at `/opt/venv` holding the installed package, copied wholesale into a runtime that carries neither `git` nor `uv`. No browser, no VNC. `compose/openoutreach/Dockerfile`. **Server deploy only**: no `BUILD_ENV`, no dev extras, no tests in the image, and the compose file mounts only `./data` (the code is what the image was built from).
- **CI/CD**: `.github/workflows/tests.yml` (native pytest on 3.12), `deploy.yml` (**every push to `main`**, plus `v*` tags → tests → build + push `ghcr.io/eracle/openoutreach` tagged `latest` + `sha-<pushed tip>` → `repository-dispatch: image-updated` to the hub repo). **A `v*` tag also publishes to PyPI** via trusted publishing (`publish-pypi`, environment `pypi`) — that job is the release, and it is the one thing `main` does not do. **There is still no release gate on the image: merging to `main` republishes `:latest`**, so code *and schema migrations* reach anyone pulling `latest` on merge. No `v*` tag has ever been cut.
